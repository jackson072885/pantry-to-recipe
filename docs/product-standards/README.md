# Product Standards

This folder contains the operating standards used to evaluate, protect, and improve recipe quality in Pantry to Plate.

These are not background notes or optional reference docs. They are working product standards used to decide what recipes deserve to exist in the app, what recipes should be repaired, and what recipes should be removed.

## Files in this folder

### `recipe-existence-doctrine.md`
The core doctrine for recipe quality in Pantry to Plate.

This document defines:
- what kind of product Pantry to Plate is
- what a recipe must do to deserve a place in the app
- the Recipe Existence Standards
- the keep / repair / remove classification rule
- straight-to-remove triggers
- the core principle that a recipe must be both cookable and recommendable

Use this document when:
- defining recipe quality expectations
- judging whether a recipe belongs in the product
- setting product direction for recommendation quality
- guiding audits, rewrites, and deletions
- writing prompts for structured recipe review work

### `recipe-audit-sheet.md`
The practical worksheet used to evaluate individual recipes against the doctrine.

This document provides:
- a recipe-by-recipe audit structure
- an Existence Gate
- pass/fail review sections for each standard
- repair-worthiness checks
- straight-to-remove review
- final keep / repair / remove classification
- repair notes
- a quick-audit version for faster batch review

Use this document when:
- auditing individual recipes
- reviewing surfaced dinner recommendations
- deciding whether to keep, repair, or remove a recipe
- documenting exact reasons for recipe decisions
- preparing structured recipe cleanup work

### `.docx` versions
The `.docx` files are polished document versions of the doctrine and audit sheet.

Use the `.docx` files when:
- sharing documents outside the repo
- reviewing in Word
- printing
- sending polished copies to collaborators

Use the `.md` files as the editable source-of-truth versions inside the repo unless there is a specific reason not to.

## How these standards should be used

These standards should be applied to any recipe that is:
- surfaced on Home
- shown as a recommended dinner option
- likely to receive high user exposure
- being considered for repair, rewrite, or removal
- being added to the dataset for future use

The intended order of use is:

1. Read the doctrine
2. Audit the recipe against the standards
3. Classify the recipe as Keep, Repair, or Remove
4. Repair only if the recipe can be made to pass completely
5. Remove recipes that cannot be made to pass completely or are not worth the effort

## Core rule

A recipe may exist in Pantry to Plate only if it passes every Recipe Existence Standard completely.

- If it passes completely, keep it.
- If it can be made to pass completely, repair it.
- If it cannot be made to pass completely, remove it.

## Practical guidance

When in doubt:
- do not protect weak recipes
- do not keep filler for count
- do not repair recipes that are technically fixable but not worth the effort
- do not let redundancy weaken the dataset
- do prioritize trust, clarity, dinner value, and recommendation-worthiness

Pantry to Plate is not a recipe storage system. It is a dinner decision product.

That means a recipe does not deserve to exist merely because it is technically valid. It must deserve to be chosen, trusted, and recommended.
